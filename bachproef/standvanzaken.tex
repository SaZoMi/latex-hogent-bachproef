This chapter provides the theoretical background necessary to understand the contributions of this thesis. It begins with a detailed treatment of Large Language Models (LLMs), covering their architecture, internal representations, inference behaviour, and the techniques that make them capable of autonomous, tool-assisted reasoning. This foundation is essential for appreciating why standardised integration protocols are needed, which leads to the subsequent sections on the Model Context Protocol and its client and server architectures. The chapter concludes by discussing known limitations and the orchestration patterns that practitioners use to work around them.

\section{Large Language Models}
\label{sec:llm}

Large Language Models are neural networks trained on vast corpora of text with the objective of predicting the next token in a sequence. Through this deceptively simple training signal, such models acquire broad linguistic competence, world knowledge, and the ability to perform complex reasoning tasks at inference time \autocite{brown2020gpt3}. Understanding the internals of these systems—from their architectural foundations to the strategies used to sample from them—is a prerequisite for understanding how they can be extended with external tools and structured protocols such as the Model Context Protocol discussed in subsequent sections.

\subsection{Transformer Architecture and Self-Attention}
\label{subsec:transformer}

\subsubsection{The Transformer Model}

The Transformer, introduced by \textcite{vaswani2017attention} in 2017, marked a decisive departure from the recurrent and convolutional architectures that had dominated sequence modelling. Rather than processing tokens sequentially, the Transformer operates on entire sequences in parallel, relying exclusively on attention mechanisms to model dependencies between positions. The original architecture consists of an encoder stack that builds contextual representations of the input and a decoder stack that generates output tokens auto-regressively; modern generative LLMs typically retain only the decoder portion.

Each layer in the stack contains two principal sub-components: a \textbf{multi-head self-attention} module and a position-wise \textbf{feed-forward network}, each followed by a residual connection and layer normalisation. This design allows very deep networks to be trained stably and enables information from any position in the sequence to influence any other position in a single layer pass \autocite{vaswani2017attention}. The parallel nature of the computation makes the Transformer highly amenable to modern GPU hardware, enabling training on datasets orders of magnitude larger than was practical with recurrent architectures. As of 2024, virtually every competitive LLM—including GPT-4, LLaMA, Gemini, and Claude—is based on variants of this architecture.

The feed-forward sub-network, applied independently to each position, typically expands the representation to a higher-dimensional space and then projects it back, using a non-linear activation such as GeLU or SwiGLU. The interaction between the attention mechanism and the feed-forward sublayers is understood to implement a form of key--value memory, where the attention heads retrieve relevant information and the feed-forward layers act as pattern stores \autocite{vaswani2017attention}.

\subsubsection{Self-Attention Mechanism}

The core innovation of the Transformer is \textbf{self-attention}, which computes a weighted sum of value vectors, where the weights are derived from the compatibility between query and key vectors. Formally, given queries $Q$, keys $K$, and values $V$, the attention function is:

\[
\text{Attention}(Q, K, V) = \text{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right)V
\]

where $d_k$ is the dimensionality of the key vectors and the scaling factor $\sqrt{d_k}$ prevents the dot products from growing too large, which would push the softmax into regions of very small gradients \autocite{vaswani2017attention}. Because queries, keys, and values are derived from the same sequence of representations, the mechanism is called \emph{self-attention}: each position attends to all other positions in the sequence, including itself.

\textbf{Multi-head attention} runs several attention functions in parallel on linearly projected subspaces and concatenates the results. This allows the model to jointly attend to information from different representation subspaces at different positions, capturing a richer variety of relationships—such as syntactic dependencies, coreference, and semantic similarity—than a single attention head could express \autocite{vaswani2017attention}. Because self-attention is permutation-equivariant by construction, positional information must be injected separately; the original Transformer uses sinusoidal positional encodings, while most modern models employ learned or rotary positional embeddings (discussed further in Section~\ref{subsec:context}).

\subsection{Tokenization and Representations}
\label{subsec:tokenization}

\subsubsection{Tokenization Techniques}

Before a language model can process text, the raw character stream must be converted into a discrete sequence of tokens drawn from a fixed vocabulary. Early models operated on whole words, which led to large vocabularies, poor generalisation to rare words, and inability to handle out-of-vocabulary terms. \textbf{Subword tokenization} was introduced to resolve this tension: frequent words are represented as single tokens, while rare or morphologically complex words are split into smaller, reusable pieces that appear across many contexts.

\textbf{Byte Pair Encoding (BPE)}, adapted for neural machine translation by \textcite{sennrich2016bpe}, starts with a character-level vocabulary and iteratively merges the most frequent adjacent pair of symbols until the desired vocabulary size is reached. The algorithm is simple, deterministic, and language-agnostic; it powers the tokenisers of GPT-2, GPT-3, GPT-4, LLaMA, and many other models. A related algorithm, \textbf{WordPiece} \autocite{schuster2012wordpiece}, maximises corpus log-likelihood rather than raw pair frequency, and is used in BERT and Google's translation systems. \textbf{SentencePiece} \autocite{kudo2018sentencepiece} generalises both approaches by treating the input as a raw character stream without any language-specific pre-tokenisation, making it well-suited for multilingual and character-rich languages such as Japanese and Chinese.

The choice of tokenisation scheme has a significant practical impact on model performance. A vocabulary that is too coarse forces the model to represent common concepts with multiple tokens, inflating sequence lengths and context window consumption; a vocabulary that is too fine-grained increases computational cost and may prevent the model from learning useful lexical patterns. Modern LLMs therefore use carefully tuned vocabulary sizes, typically between 32,000 and 100,000 tokens, that balance these competing pressures \autocite{sennrich2016bpe}.

\subsubsection{Vector Embeddings}

Once a sequence has been tokenised, each token index is mapped to a dense, real-valued vector called an \textbf{embedding}. The foundational insight that words can be represented as points in a continuous semantic space was demonstrated by \textcite{mikolov2013word2vec}, whose Word2Vec model showed that simple arithmetic on embedding vectors could capture analogy relationships such as \emph{king} $-$ \emph{man} $+$ \emph{woman} $\approx$ \emph{queen}. Similarly, GloVe \autocite{pennington2014glove} derived embeddings from global co-occurrence statistics, showing that distributional semantics could be encoded into geometric structure.

These \emph{static} embeddings assign a single vector to each word regardless of context. The limitations of this approach—most notably the inability to distinguish word senses—were addressed by \textbf{contextual embeddings}, introduced by \textcite{devlin2019bert} with BERT. In BERT, a deep bidirectional Transformer processes the full input sequence, producing a distinct representation for each token that reflects its surrounding context. The token representations at each Transformer layer can be understood as progressively refined, context-sensitive encodings that capture syntax at lower layers and semantics at higher layers. In modern auto-regressive LLMs, the final hidden state of each token position serves an analogous role, encoding the accumulated contextual information that the decoder uses to predict the next token.

\subsection{Inference in Large Language Models}
\label{subsec:inference}

\subsubsection{Deterministic and Stochastic Decoding}

Given a trained model and an input prompt, inference consists of repeatedly sampling the next token from the model's conditional probability distribution until a stopping criterion is met. The simplest strategy is \textbf{greedy decoding}, which always selects the single most probable next token. Greedy decoding is deterministic and fast, but it is locally optimal rather than globally optimal: choosing the highest-probability token at each step does not guarantee the highest-probability complete sequence, and greedy outputs tend to be repetitive and degenerate \autocite{holtzman2020nucleus}.

\textbf{Beam search} maintains a set of $B$ candidate sequences (the \emph{beam}) and at each step expands each candidate with its top-$B$ continuations, retaining only the $B$ globally highest-scoring partial sequences. Beam search is widely used in tasks requiring high-precision, constrained generation such as machine translation and summarisation, where fidelity to the source matters more than diversity. However, \textcite{holtzman2020nucleus} showed that maximisation-based methods systematically produce text that is locally plausible but globally incoherent, motivating the development of stochastic alternatives for open-ended generation.

\subsubsection{Sampling Strategies}

\textbf{Temperature sampling} scales the model's logits by a temperature parameter $T$ before applying the softmax, thereby controlling the sharpness of the distribution. A temperature of $T = 1$ reproduces the model's raw distribution; values below 1 concentrate probability mass on high-probability tokens, making the output more deterministic; values above 1 flatten the distribution, increasing diversity and creativity at the cost of coherence \autocite{holtzman2020nucleus}.

\textbf{Top-$k$ sampling} truncates the distribution to the $k$ most probable tokens before normalisation, preventing the model from sampling from the long tail of improbable vocabulary items. A complementary method, \textbf{top-$p$ (nucleus) sampling}, introduced by \textcite{holtzman2020nucleus}, instead selects the smallest set of tokens whose cumulative probability mass exceeds a threshold $p$. Because the size of the nucleus adapts dynamically to the model's confidence—shrinking when the model is certain and expanding when it is uncertain—top-$p$ sampling produces more natural and varied text than fixed top-$k$ sampling. In practice, modern LLM deployments combine temperature scaling with top-$p$ sampling, and sometimes top-$k$ as an additional filter, to balance coherence with diversity.

\subsection{Context Window and Sequence Handling}
\label{subsec:context}

A fundamental constraint of Transformer-based LLMs is the \textbf{context window}: the maximum number of tokens the model can process in a single forward pass. This limit arises because the quadratic complexity of self-attention with respect to sequence length makes longer contexts computationally expensive, and because positional representations must generalise to lengths seen during training. Early models such as GPT-2 were limited to 1,024 tokens; contemporary models such as GPT-4o, Gemini 1.5 Pro, and Claude 3.5 support context windows of 128,000 to over 1,000,000 tokens, enabled by algorithmic and hardware advances.

A key enabler of long-context models is \textbf{Rotary Positional Embedding (RoPE)}, proposed by \textcite{su2021rope}. Instead of adding absolute positional vectors to token embeddings, RoPE encodes position by rotating the query and key vectors in the attention computation, such that the inner product between a query at position $m$ and a key at position $n$ depends only on their relative distance $m - n$. This relative-position property allows the attention mechanism to generalise more gracefully to sequence lengths not seen during pretraining, and RoPE has been adopted in LLaMA, Mistral, and most other open-weight LLMs. Extensions such as YaRN further extend the effective context length by adjusting the RoPE base frequency during fine-tuning \autocite{su2021rope}.

For tasks that exceed even large context windows—such as processing entire codebases or long documents—practitioners resort to additional strategies. \textbf{Sliding window attention} processes the sequence in overlapping chunks, with each chunk attending only to a local neighbourhood; this reduces complexity but may lose long-range dependencies. \textbf{Retrieval-augmented generation (RAG)} offloads long-term memory to an external vector store: relevant passages are retrieved via semantic similarity search and injected into the context at query time, effectively giving the model access to an arbitrarily large external knowledge base without requiring a proportionally large context window \autocite{wang2023agents}.

\subsection{Prompt Engineering}
\label{subsec:prompt}

\subsubsection{Instruction Design}

\textbf{Prompt engineering} refers to the practice of deliberately crafting natural language inputs to elicit desired behaviour from a language model without modifying its weights. Because LLMs are sensitive to the phrasing, structure, and content of their input, small changes to a prompt can have large effects on the quality and form of the output. The field has matured rapidly, developing a body of techniques that are now considered standard practice in production deployments \autocite{brown2020gpt3}.

The most fundamental prompting distinction is between \textbf{zero-shot} prompting, in which the task is described solely through a textual instruction, and \textbf{few-shot} prompting, in which a small number of input--output demonstrations precede the test query. \textcite{brown2020gpt3} showed that GPT-3, at sufficient scale, could perform competitive few-shot learning on a wide range of tasks from only a handful of examples, without any gradient updates. \textbf{Chain-of-thought (CoT) prompting}, introduced by \textcite{wei2022cot}, demonstrated that instructing the model to emit intermediate reasoning steps before producing a final answer substantially improved performance on arithmetic, commonsense, and symbolic reasoning tasks, apparently by exploiting the model's capacity to perform multi-step computation in the generation space. Effective instruction design therefore involves not only stating what the model should produce but also guiding the form of its internal reasoning process.

\subsubsection{Context Construction}

Beyond the task instruction itself, the surrounding context—system messages, retrieved documents, conversation history, and tool outputs—forms an equally important part of the prompt. Practitioners must manage the finite context window by selecting which information to include, how to order it, and how to format it. Research has shown that models are sensitive to the position of relevant information within the context: facts placed at the beginning or end of a long context are recalled more reliably than facts buried in the middle, a phenomenon sometimes called the \emph{lost-in-the-middle} problem \autocite{zhou2025prompt}.

Structured prompt templates—separating system instructions, retrieved context, few-shot examples, and the user query into clearly delimited sections—improve both reliability and maintainability. In agentic settings, the context must additionally encode the agent's current state, the results of previously invoked tools, and any accumulated scratchpad reasoning, making context construction a dynamic, multi-turn process rather than a one-off design task. \textcite{zhou2025prompt} identify clarity of task description, consistency of formatting, and inclusion of relevant exemplars as the factors most predictive of prompt effectiveness across diverse task types.

\subsection{Agents and Autonomous Behavior}
\label{subsec:agents}

\subsubsection{Agent Architectures}

An \textbf{LLM-based agent} is a system in which a language model serves as a central reasoning engine that perceives an environment, plans a course of action, invokes tools or sub-agents, and iterates until a goal is achieved. \textcite{wang2023agents} identify four core modules common to most agent architectures: a \emph{profiling} module that defines the agent's role and persona; a \emph{memory} module that stores short-term context and long-term experience; a \emph{planning} module that decomposes complex goals into manageable steps; and an \emph{action} module that executes plans by calling tools, APIs, or other agents.

The memory module is particularly consequential for multi-step tasks. Short-term memory maps naturally onto the context window, while long-term memory requires an external store—typically a vector database—from which relevant information is retrieved as needed. The planning module may operate reactively, generating the next action based on the current state, or proactively, constructing a full plan before execution begins. The action module translates the model's textual output into concrete operations: writing to files, executing code, querying APIs, or spawning sub-agents. Together, these modules form a closed loop in which perception, reasoning, and action are tightly integrated \autocite{wang2023agents}.

\subsubsection{Reasoning-Action Loops}

The \textbf{ReAct} framework, proposed by \textcite{yao2022react}, provides a general paradigm for interleaving reasoning and acting in LLM agents. At each step the model produces a \emph{thought}—a free-form natural language trace of its current reasoning—followed by an \emph{action} that invokes an external tool, and then observes the tool's \emph{response} before continuing. This Thought--Action--Observation loop allows the model to dynamically adapt its reasoning in response to new information, reducing the hallucination and error propagation that afflict purely generative approaches.

Empirically, \textcite{yao2022react} demonstrated on question-answering and fact-verification benchmarks that ReAct substantially outperforms both chain-of-thought prompting alone and pure action-based approaches, because the interleaved reasoning helps the model detect and correct mistakes before they compound. The ReAct pattern has become foundational in agentic frameworks such as LangChain, AutoGPT, and many MCP-based systems, where the tool invocation protocol provides the structured action interface over which the Thought--Action--Observation loop operates.

\subsection{Planning Approaches}
\label{subsec:planning}

\subsubsection{Single-Shot Prompting}

The simplest planning strategy is \textbf{single-shot} or \textbf{zero-shot} prompting: the model is presented with a task description and expected to produce a complete response in a single generation pass. While effective for straightforward tasks, this approach falters on problems that require exploration, backtracking, or the integration of information gathered across multiple steps. The linear, left-to-right generation process of auto-regressive LLMs means that an early mistake cannot be corrected without discarding the entire generation \autocite{yao2023tot}.

Chain-of-thought prompting partially addresses this limitation by encouraging the model to externalise its reasoning before committing to a final answer, but the reasoning trace is still generated left-to-right in a single pass without any exploration of alternative paths. For straightforward, well-specified tasks—code completion, summarisation, question answering—single-shot prompting with a well-constructed prompt often achieves satisfactory results with minimal latency and cost, making it the default strategy in production systems \autocite{wei2022cot}.

\subsubsection{Iterative and Planning-Based Methods}

For tasks that require genuine deliberation and exploration, \textbf{iterative} and \textbf{tree-structured} planning methods offer more robust solutions. \textcite{yao2023tot} proposed \textbf{Tree of Thoughts (ToT)}, which generalises chain-of-thought prompting by allowing the model to explore multiple reasoning paths in a tree structure, evaluating intermediate states and backtracking when a branch appears unpromising. On tasks such as the Game of 24 and mini crosswords, ToT with GPT-4 achieved 74\% success compared to 4\% for standard chain-of-thought prompting, demonstrating the value of deliberate search for hard combinatorial problems.

The \textbf{Plan-and-Execute} pattern adopts a two-phase approach: a \emph{planner} LLM first generates a high-level, multi-step plan; an \emph{executor} LLM (or the same model in a separate call) then carries out each step in sequence, updating the plan if new information warrants a revision. This separation of concerns aligns with classical AI planning: the planner reasons at an abstract level, while the executor deals with concrete tool invocations and environmental interactions \autocite{wang2023agents}. The pattern is particularly well-suited to complex software development tasks, where upfront planning reduces the risk of embarking on an implementation path that violates architectural constraints discovered only later.

\subsection{Tool and Function Calling}
\label{subsec:toolcalling}

\subsubsection{Structured Outputs}

A language model's natural output medium is unstructured free text. For tool invocation and system integration, however, structured and machine-parseable outputs are required. \textbf{Structured output} capabilities allow a model to emit JSON or other typed data that conforms to a developer-supplied schema, enabling reliable downstream processing without fragile regex-based parsing. OpenAI's Structured Outputs API, released in 2024, guarantees that model outputs exactly match a provided JSON Schema by combining constrained decoding with schema-aware training, eliminating the class of integration errors caused by malformed or schema-violating model responses \autocite{schick2023toolformer}.

The ability to produce structured outputs is a prerequisite for robust tool use. Without it, downstream systems must defensively parse free-text descriptions of intended actions, which introduces ambiguity and brittleness. Structured outputs transform the model's interface from a prose channel into a typed API, a shift that is conceptually central to the Model Context Protocol discussed in subsequent sections, where every tool call and its result must conform to well-defined schemas.

\subsubsection{Tool Invocation Mechanisms}

\textbf{Function calling} was introduced by OpenAI in June 2023 as a mechanism by which models fine-tuned to understand tool schemas could emit structured tool-invocation requests as part of their generation. A developer provides a list of available functions—each described by a name, a natural language description, and a JSON Schema for its parameters—and the model decides, based on context, whether to invoke a tool and with which arguments. The model does not execute the function itself; it emits a structured request that the application layer executes, feeds the result back into the context, and then prompts the model to continue \autocite{schick2023toolformer}.

\textcite{schick2023toolformer} showed, in the Toolformer model, that language models can learn to use APIs in a self-supervised manner: the model is trained on data that annotates when and how API calls should be inserted into the generation stream, teaching it to recognise situations in which an external tool would improve its prediction. This demonstrated that tool use is not merely a prompt-engineering trick but a learnable behaviour that can be instilled through training. Modern instruction-tuned models such as GPT-4, Claude, and Gemini receive explicit function-calling training, making them reliable orchestrators of complex, multi-tool workflows. The standardisation of these invocation mechanisms across diverse tools and providers is precisely the problem that the Model Context Protocol is designed to solve.



\section{Model Context Protocol}
\label{sec:mcp}

The Model Context Protocol (MCP) is an open protocol introduced by Anthropic on 25 November 2024 with the explicit goal of standardising how large language models connect to external tools, data sources, and services \autocite{hou2025modelcontextprotocolmcp}. Where previous approaches required every AI application to implement its own bespoke connectors for every external system it wished to access, MCP proposes a single, provider-neutral interface that any compliant host and any compliant server can speak without further negotiation. Technically, MCP is built on JSON-RPC 2.0, a lightweight remote-procedure-call specification that allows both synchronous request--response exchanges and asynchronous notifications over a variety of transports, from local standard-input/output pipes to HTTP with server-sent events \autocite{Ray_2025}. Anthropic released the protocol as open source together with reference server implementations for widely used enterprise systems—including GitHub, Google Drive, Slack, and PostgreSQL—and software development kits in Python, TypeScript, Java, and C\#, thereby lowering the barrier to adoption from the outset \autocite{Sekar2026MCP}. The design draws explicit inspiration from the Language Server Protocol (LSP), which solved an analogous standardisation problem in the developer-tooling space by defining a single protocol for communication between code editors and language intelligence backends; MCP applies the same architectural insight to the richer, more dynamic context of AI agent systems \autocite{hou2025modelcontextprotocolmcp}.

\subsection{The MxN Problem}
\label{subsec:mxn}

Before MCP, the integration of AI models with external tools exhibited a combinatorial explosion commonly referred to as the M$\times$N problem. Given $M$ distinct AI model deployments and $N$ distinct external tools or data sources, a fully connected ecosystem requires up to $M \times N$ separate integration implementations, each encoding assumptions about the specific model's function-calling schema, the specific tool's API conventions, authentication mechanisms, and error-handling behaviours \autocite{Ray_2025}. In practice, an organisation operating three distinct LLM-based products and fifteen enterprise data systems was obliged to maintain as many as forty-five independent connector codebases, each with its own update cycle and failure modes. Because no shared contract existed between model providers and tool providers, every new model release potentially invalidated existing connectors, and every new tool required fresh integration work for each model already deployed \autocite{hou2025modelcontextprotocolmcp}.

The absence of a shared standard produced two compounding pathologies. First, integration effort scaled multiplicatively rather than additively: adding a single new tool to an existing ecosystem of $M$ models demanded $M$ new connectors, and adding a single new model demanded $N$ new connectors. Second, the resulting connector landscape was fragile and heterogeneous, with each implementation being a one-off engineering project that produced nothing reusable when the next model or tool entered the picture \autocite{Sekar2026MCP}. Anthropic's announcement of MCP explicitly identified this combinatorial burden as the primary motivation for the protocol, noting that even the most capable frontier models were effectively ``trapped behind information silos and legacy systems'' because the cost of integrating each new data source remained prohibitively high \autocite{hou2025modelcontextprotocolmcp}.

MCP resolves the M$\times$N problem by introducing a universal intermediary layer that both sides of the integration agree to speak. Each tool or data source exposes a single MCP server implementation; each AI application embeds a single MCP client. Because both sides communicate over the same protocol, any MCP-compliant client can connect to any MCP-compliant server without additional negotiation, reducing the total integration surface from $M \times N$ to $M + N$: one client-side integration per AI application, and one server-side integration per external system \autocite{Ray_2025}. This is conceptually analogous to what the USB-C standard achieved in consumer electronics, where a single physical and logical interface replaced a proliferation of proprietary charging and data connectors; the same insight—that a universal standard benefits the entire ecosystem even when it requires each participant to adopt a new interface—underlies MCP's design philosophy \autocite{Sekar2026MCP}. The analogy extends to the Language Server Protocol, which transformed the $M \times N$ matrix of editor-to-language integrations into an $M + N$ problem by specifying how any editor and any language server should communicate, enabling VS Code, Vim, Emacs, and dozens of other editors to gain support for hundreds of programming languages through a single protocol layer \autocite{hou2025modelcontextprotocolmcp}.

The practical impact of this architectural shift becomes apparent when considering ecosystem growth. Under the pre-MCP regime, each new entrant on either side of the integration—whether a new model provider or a new tool vendor—faced a large and growing backlog of custom connector work before it could participate in the ecosystem. Under MCP, a new tool vendor ships one MCP server and immediately becomes reachable by every existing MCP-capable AI client; a new model provider ships one MCP client and immediately gains access to every existing MCP server. \textcite{Sekar2026MCP} characterises this property as the protocol's most consequential contribution: by aligning the incentives of model providers, tool vendors, and application developers around a single open standard, MCP transforms integration from a bilateral negotiation into a public good. The subsequent rapid industry adoption—with OpenAI integrating MCP into its Agents SDK in March 2025, and Google DeepMind following in April 2025—confirmed that the protocol had achieved the critical mass necessary to function as a genuine standard rather than merely a vendor-specific convention \autocite{Ray_2025}.



\section{MCP Client Architecture}
\label{sec:mcp-client}

In the Model Context Protocol, the term \emph{client} refers to the software component that lives inside a host application and manages a stateful, one-to-one connection with a single MCP server. The host itself—which may be an integrated development environment, a conversational chatbot interface, an autonomous agent framework, or any other LLM-powered application—instantiates one client instance per server it wishes to connect to, so a single host typically operates a collection of concurrent client sessions \autocite{mcpspec2025}. This architectural separation between host and client is deliberate: the host is responsible for aggregating information across all its client connections, enforcing security policies, and coordinating the interaction between the language model and the outside world, while each individual client acts as a dedicated protocol handler whose sole responsibility is to faithfully relay JSON-RPC messages to and from its paired server \autocite{Ray_2025}.

The lifecycle of a client session is strictly ordered and consists of three phases: initialisation, operation, and shutdown. During initialisation the client sends an \texttt{initialize} request that declares the protocol version it supports and the set of capabilities it can honour; the server responds with its own protocol version and the list of primitives it exposes; and the client confirms readiness by sending an \texttt{initialized} notification \autocite{mcpspec2025}. Capabilities negotiated in this handshake govern the entire subsequent session—a server may only invoke server-to-client primitives that the client has explicitly declared, and a client may only use server-side features that the server has advertised. This capability-based negotiation ensures that both parties have an unambiguous, shared understanding of what the protocol session supports without requiring any out-of-band coordination \autocite{Sekar2026MCP}. The client primitives defined by the specification—sampling, elicitation, and roots—are the three mechanisms through which a server can reach back into the host environment, and each is discussed in detail in the subsections that follow.

\subsection{Sampling Strategies}
\label{subsec:mcp-sampling}

Sampling is a server-to-client primitive that inverts the conventional direction of tool invocation: instead of the client instructing the server to do something, the server asks the client to perform an LLM completion on its behalf. This capability is what enables fully server-side agentic loops in MCP—a server processing a complex, multi-step task can at any point pause its execution, compose a prompt, and request that the connected language model reason about the current state before continuing \autocite{mcpspec2025sampling}. The mechanism is deliberately kept on the client side so that the host application retains complete authority over which model is queried, on what terms, and at what cost; servers obtain AI capabilities without ever possessing API keys or direct model access of their own.

To invoke the sampling primitive the server sends a \texttt{sampling/createMessage} request over the established JSON-RPC channel. The request body is a structured object whose core field is \texttt{messages}, an array of role-annotated content blocks—each block may carry plain text, a base64-encoded image, or audio data—that constitute the prompt the server wishes to submit to the model \autocite{mcpspec2025sampling}. Alongside \texttt{messages} the server may specify an optional \texttt{systemPrompt} string, a \texttt{maxTokens} integer that caps the response length, a \texttt{temperature} float that controls output stochasticity, and a \texttt{stopSequences} array of strings at which generation should halt. Because the client and server may be connected to entirely different model providers with distinct offerings, the protocol also defines a \texttt{modelPreferences} object that allows the server to express abstract preferences rather than a hard model requirement: three normalised priority scalars—\texttt{costPriority}, \texttt{speedPriority}, and \texttt{intelligencePriority}, each ranging from zero to one—describe what the server values most in the completion, while an ordered \texttt{hints} array may suggest specific model names or families as advisory preferences \autocite{mcpspec2025sampling}. The client may map a hint such as \texttt{claude-3-sonnet} to a semantically equivalent model from a different provider if the hinted model is unavailable, preserving the server's intent without coupling it to a specific vendor's offering. The response to a successful \texttt{sampling/createMessage} carries the \texttt{role}, the \texttt{content} of the generated turn, the identifier of the \texttt{model} that produced it, and a \texttt{stopReason} indicating how generation terminated (\texttt{endTurn}, \texttt{stopSequence}, or \texttt{maxTokens}).

The specification places a strong emphasis on human oversight throughout the sampling workflow. The MCP architecture documentation prescribes that there should always be a human in the loop with the ability to deny sampling requests, and that client implementations should provide a user interface that makes it easy and intuitive to review them \autocite{mcpspec2025sampling}. In practice this means the client is expected to present the proposed prompt to the user before forwarding it to the language model, allow the user to edit or reject the request, and then—after the model generates its response—present that response for a second round of human review before returning it to the server. This two-checkpoint design prevents a malicious or misconfigured server from silently using the user's model quota, injecting adversarial content into the LLM context, or extracting sensitive information through cleverly crafted completions \autocite{hou2025modelcontextprotocolmcp}. The client is also advised to implement rate limiting on incoming sampling requests and to validate message content before dispatch, recognising that sampling constitutes a powerful capability that must be exercised with care.

\subsection{Elicitation Mechanisms}
\label{subsec:mcp-elicitation}

Elicitation is the protocol's mechanism for servers to solicit additional information from the end user at runtime, interactively and mid-task, without requiring that all necessary information be provided upfront in the initial request. Where sampling delegates reasoning to the language model, elicitation delegates information gathering to the human: a server that discovers it needs a username, a configuration value, or a user decision to proceed can issue an \texttt{elicitation/create} request over the client channel and block until the user responds \autocite{mcpspec2025elicitation}. This capability is essential for building interactive agentic workflows in which the scope or parameters of a task are not fully known at the outset, and it is a formal, protocol-level replacement for the ad-hoc convention of embedding clarifying questions inside tool descriptions or system prompts.

The specification defines two elicitation modes. In \emph{form mode}, the server submits an \texttt{elicitation/create} request containing a human-readable \texttt{message} string that explains why the information is needed, together with a \texttt{requestedSchema} object that describes the expected response as a flat JSON Schema \autocite{mcpspec2025elicitation}. The schema is intentionally restricted to primitive property types—strings (with optional format constraints such as \texttt{email}, \texttt{uri}, \texttt{date}, or \texttt{date-time}), numbers and integers (with optional \texttt{minimum} and \texttt{maximum} bounds), booleans, and single-select or multi-select enumerations—because this subset is sufficiently expressive for the most common data-collection scenarios while remaining simple enough for any client to render as a native form without requiring a full-featured JSON Schema renderer. The client uses the schema to generate an appropriate input form, pre-populate fields where the schema supplies default values, and validate user input before transmission. \emph{URL mode} elicitation, introduced in the November 2025 revision of the specification, addresses a different class of interactions—OAuth authorisation flows, payment processing, and the entry of secrets such as API keys—for which it would be inappropriate for the data to pass through the MCP client at all \autocite{mcpspec2025elicitation}. In URL mode the server provides a \texttt{url} and a unique \texttt{elicitationId}; the client shows the target domain to the user, obtains explicit consent, and opens the URL in a secure browser context; the subsequent interaction happens entirely out of band between the user's browser and the server, and the server may optionally signal completion by sending a \texttt{notifications/elicitation/complete} notification carrying the original \texttt{elicitationId}.

Elicitation responses follow a three-action model: \texttt{accept}, \texttt{decline}, and \texttt{cancel}. An \texttt{accept} response in form mode carries a \texttt{content} object containing the submitted field values; a \texttt{decline} signals that the user explicitly refused to provide the requested information; and \texttt{cancel} indicates that the user dismissed the dialogue without making an explicit choice, a distinction that allows servers to implement context-sensitive recovery strategies such as prompting again later \autocite{mcpspec2025elicitation}. The specification imposes strict security constraints: servers must not use form mode to request passwords, API tokens, or payment credentials—such information must travel exclusively through URL mode—and clients must clearly indicate to the user which server is making the request and ensure that users can decline at any time \autocite{hou2025modelcontextprotocolmcp}. A further constraint introduced in the 2025 specification requires that all server-to-client requests, including \texttt{elicitation/create}, be sent only in association with an originating client-to-server request (such as a \texttt{tools/call} or \texttt{resources/read}), preventing servers from issuing unsolicited, standalone elicitation requests that the user did not initiate through any visible action.

\subsection{Roots and Context Initialization}
\label{subsec:mcp-roots}

Roots are the MCP mechanism through which a client communicates to a server the boundaries of the filesystem or workspace within which the server is permitted to operate. In the absence of such a declaration, a server receiving file-system access tools would have no principled basis for determining which directories are in scope for the current task; roots formalise this boundary as a first-class, protocol-level concept rather than relying on informal conventions embedded in system prompts or tool descriptions \autocite{mcpspec2025roots}. An MCP client that supports the roots capability declares this during the initialisation handshake by including a \texttt{roots} object in its capabilities payload; the \texttt{listChanged} boolean field within that object signals whether the client will emit notifications when the declared set of roots changes during the session.

The mechanism itself is straightforward. When a server wishes to discover the scope within which it should operate, it sends a \texttt{roots/list} request; the client responds with an array of root objects, each consisting of a mandatory \texttt{uri} field—which must be a \texttt{file://} URI under the current specification—and an optional human-readable \texttt{name} field for display purposes \autocite{mcpspec2025roots}. A typical IDE acting as an MCP host might declare a single root pointing to the currently open project directory; a multi-repository development environment might declare several roots, one for each repository; and a document-processing agent might expose a dedicated working directory as its sole root. Roots are not static for the duration of a session: if the user opens a different project, adds a workspace folder, or revokes access to a directory, the client emits a \texttt{notifications/roots/listChanged} notification, after which the server is expected to re-issue a \texttt{roots/list} request and update its understanding of the accessible scope accordingly \autocite{mcpspec2025roots}.

The security implications of roots are significant. Clients are required to expose only those directories for which the user has explicitly granted consent, validate all root URIs against path-traversal attacks before advertising them, and monitor root accessibility throughout the session \autocite{mcpspec2025roots}. Servers, for their part, are expected to treat the declared roots as authoritative boundaries and validate every file-system path they intend to access against the provided root list before executing any operation. This bidirectional enforcement means that a well-implemented MCP system can provide strong, user-visible guarantees about the scope of a server's file-system access—a property of considerable practical importance in agentic settings where a server might otherwise attempt to read configuration files, credentials, or other sensitive material outside the intended working scope \autocite{hou2025modelcontextprotocolmcp}. By encoding workspace boundaries in the protocol rather than in natural language instructions, roots reduce the attack surface for prompt-injection exploits that attempt to override stated restrictions through cleverly crafted tool inputs.

\subsection{Request Construction and Context Assembly}
\label{subsec:mcp-context-assembly}

The construction of the context window that is ultimately submitted to the language model is the responsibility of the host application, not of any individual client or server. Because a single host may maintain connections to multiple MCP servers simultaneously—each contributing its own set of tools, resources, and prompt templates—the host must aggregate, reconcile, and prioritise information from all of these sources before formulating the prompt that the model will process \autocite{mcpspec2025architecture}. This aggregation process, which the MCP architecture documentation calls \emph{context aggregation across clients}, is where the protocol's composability property becomes most consequential: the same model can draw on a filesystem server, a database server, and a web-search server within a single conversational turn, provided the host correctly assembles their respective contributions into a coherent context.

The assembly process proceeds in layers. At session start the host queries each connected server for its available primitives: it calls \texttt{tools/list} to enumerate callable tools, \texttt{resources/list} to discover available data sources, and \texttt{prompts/list} to retrieve any reusable prompt templates the server exposes \autocite{Sekar2026MCP}. The tool schemas returned by \texttt{tools/list}—each a JSON Schema describing the function name, its parameters, and their types—are injected into the system prompt or a dedicated tools section of the context so that the model can reason about which tools are available and how to invoke them. When the model decides to call a tool, the host routes the invocation to the appropriate client, which forwards it to the paired server; the server executes the tool and returns a structured result, which the host inserts into the conversation history as an assistant or tool-role turn before re-submitting the updated context to the model for the next generation step \autocite{mcpspec2025architecture}. Resource contents—fetched via \texttt{resources/read} in response to either explicit model requests or host-side retrieval logic—are similarly injected, typically as user-role or system-role context blocks, depending on the nature of the resource and the host's ordering conventions.

When multiple servers contribute prompt templates, tool descriptions, or resource contents simultaneously, the host bears the responsibility for managing the resulting context window budget. Because the total token capacity of the model is finite and shared among all contributors, a host operating many servers must implement a coherent prioritisation strategy: commonly, the host injects server-provided system prompts first, followed by retrieved resource contents ordered by relevance, followed by the current conversation history, and finally the tool schemas and any pending tool results \autocite{Ray_2025}. The MCP architecture specification deliberately delegates these ordering decisions to the host rather than prescribing them in the protocol, recognising that optimal prioritisation is application-specific and that enforcing a single ordering would reduce the protocol's generality. The isolation invariant is equally important: each server receives only the contextual information the host chooses to send it—servers do not have access to the full conversation history, to the outputs of other servers, or to each other's tool results—so the host's context-assembly logic also governs the information-security boundary between competing or mutually untrusting server integrations \autocite{mcpspec2025architecture}.




\section{MCP Server Architecture}
\label{sec:mcp-server}

An MCP server is a lightweight, focused process whose sole purpose is to expose capabilities—tools, resources, and prompt templates—to one or more MCP clients over the JSON-RPC 2.0 protocol. Unlike the host application, which coordinates the language model and manages user interaction, the server operates entirely on the capability-provider side of the architecture: it does not hold a direct connection to any LLM, does not have access to the full conversation history, and does not orchestrate multi-step reasoning \autocite{mcpspec2025architecture}. This strict separation of concerns keeps server implementations simple and composable—each server focuses on a narrow, well-defined domain such as file-system access, database queries, or web search—while the host assumes responsibility for aggregating contributions from multiple servers into a coherent model context. Physically, an MCP server can run as a local subprocess communicating over standard input and output (the \emph{stdio} transport), which is the dominant pattern for developer tooling, or as a remote HTTP service that pushes asynchronous notifications via Server-Sent Events (SSE) \autocite{Sekar2026MCP}. In both cases the wire format is identical JSON-RPC 2.0, and the protocol's session lifecycle—initialise, operate, shut down—proceeds in the same three-phase sequence described for clients in the preceding section.

During the initialisation handshake the server responds to the client's \texttt{initialize} request with a structured capabilities object that enumerates every server-side feature the session may use \autocite{mcpspec2025}. A server that exposes tools declares a \texttt{tools} capability; one that exposes data declares a \texttt{resources} capability with optional \texttt{subscribe} and \texttt{listChanged} sub-fields; one that emits diagnostic output declares a \texttt{logging} capability. Only capabilities that appear in this response may be exercised by the client during the session—the server is never obligated to honour requests for features it has not advertised. This capability-based access control is the protocol's primary mechanism for ensuring that both parties share a precise, up-front contract about what the session encompasses, eliminating the class of integration failures that arise when a client assumes the presence of functionality the server has not implemented \autocite{hou2025modelcontextprotocolmcp}. The following subsections examine the three major server-side capability groups—tools, resources, and logging—before turning to the cross-cutting validation and execution layer that underpins all of them.

\subsection{Tool Management}
\label{subsec:mcp-tools}

Tools are the primary active capability of an MCP server: they are discrete, executable functions that the language model can invoke to interact with external systems, perform computations, query databases, or call third-party APIs \autocite{mcpspec2025}. Each tool is defined by three mandatory fields—\texttt{name}, a unique string identifier within the server; \texttt{description}, a human-readable explanation of what the tool does and when it should be used; and \texttt{inputSchema}, a JSON Schema object that specifies the expected parameter types, required fields, and any validation constraints on the arguments the model must supply. An optional \texttt{outputSchema} field, introduced in the 2025-06-18 revision of the specification, allows the server to declare the structure of the tool's return value so that clients can perform strict schema validation of results and LLMs can better reason about how to incorporate returned data into their context \autocite{Fan2025MCPToolBenchPP}. Tool discovery proceeds through the \texttt{tools/list} method, which returns a paginated array of tool objects; the client typically injects these definitions into the system prompt or a dedicated tools section of the model context so that the language model can reason about which capabilities are available and formulate syntactically valid invocation requests \autocite{Sekar2026MCP}.

When the language model decides to invoke a tool, the client issues a \texttt{tools/call} request carrying the tool's \texttt{name} and an \texttt{arguments} object whose structure must conform to the tool's declared \texttt{inputSchema} \autocite{mcpspec2025}. The server executes the underlying operation and returns a result containing a \texttt{content} array—which may hold text blocks, base64-encoded image or audio data, inline resource embeddings, or links to separately retrievable resources—along with an \texttt{isError} boolean that distinguishes successful execution from application-level failures. This two-level error model is an important design feature: a network-layer or validation failure surfaces as a standard JSON-RPC error response, whereas a business-logic failure—such as an API rate-limit being exceeded or a query returning no rows—is reported inside a successful JSON-RPC response with \texttt{isError} set to \texttt{true} and a human-readable explanation in the content, allowing the language model to reason about the failure and attempt a recovery strategy rather than treating it as a fatal protocol fault \autocite{Ray_2025}. If the set of available tools changes at runtime—for instance because a plugin is loaded or unloaded—a server that has declared \texttt{listChanged: true} in its capabilities emits a \texttt{notifications/tools/list\_changed} notification, prompting the client to re-issue \texttt{tools/list} and refresh its tool registry before the next model turn.

Tool definitions may optionally carry an \texttt{annotations} object containing behavioural hints that help clients and hosts make informed decisions about how and when to invoke the tool. The specification defines four hint fields: \texttt{readOnlyHint}, which signals that the tool does not modify external state; \texttt{destructiveHint}, which warns that the tool may perform irreversible side-effects such as deleting records or sending network requests; \texttt{idempotentHint}, which indicates that repeated invocations with identical arguments produce the same result; and \texttt{openWorldHint}, which communicates that the tool interacts with entities beyond a closed, enumerable set—for example, an internet search tool whose result space is unbounded \autocite{Hasan2025MCPFirstGlance}. These annotations are explicitly advisory and untrusted by default: the specification requires that clients treat annotations as informational hints from the server rather than verified guarantees, precisely because a malicious or misconfigured server could misrepresent the safety profile of a destructive operation \autocite{mcpspec2025}. Hosts can nevertheless use annotations to implement human-in-the-loop confirmation flows—prompting the user for approval before calling any tool whose \texttt{destructiveHint} is \texttt{true}—while allowing \texttt{readOnly} tools to execute automatically, thereby balancing automation with safety in a principled, protocol-native way.

\subsection{Resource Management}
\label{subsec:mcp-resources}

Resources are the MCP server's mechanism for exposing data and content to clients, in contrast to tools, which expose executable actions. Where a tool encapsulates a computation the model can trigger, a resource is a named, addressable unit of information the model can read to enrich its context—examples include source files, database schemas, API documentation, configuration snapshots, or the live output of a monitoring dashboard \autocite{mcpspec2025}. Every resource is uniquely identified by a URI that follows the conventions of RFC 3986; the specification standardises several URI schemes for common cases, including \texttt{file://} for filesystem paths, \texttt{https://} for web-accessible documents, and \texttt{git://} for version-control objects, while permitting servers to define custom schemes for domain-specific resource types \autocite{Sekar2026MCP}. Clients discover available resources through the \texttt{resources/list} method, which returns a paginated array of resource descriptors, each carrying a mandatory \texttt{uri}, an optional human-readable \texttt{name}, an optional \texttt{description}, and an optional \texttt{mimeType} that hints at the content format. Resources may additionally carry annotations—\texttt{audience} (either \texttt{user}, \texttt{assistant}, or both), \texttt{priority} (a normalised 0–1 float), and \texttt{lastModified} (an ISO 8601 timestamp)—which the host can use to decide which resources to include in the context window, in what order, and with what precedence when the total available content exceeds the model's token budget.

To retrieve the content of a specific resource, a client sends a \texttt{resources/read} request containing the resource's URI \autocite{mcpspec2025}. The server responds with a \texttt{contents} array whose items are typed content blocks: text resources carry a \texttt{text} field with the raw string content, while binary resources carry a \texttt{blob} field with base64-encoded data and a \texttt{mimeType} specifier. A single \texttt{resources/read} response may return multiple content blocks if, for example, a request to a directory URI yields the content of several files, or if the server chooses to return both a structured representation and a human-readable summary of the same underlying data. For resources whose content changes over time, the protocol defines a subscription mechanism: a client that has declared support for resource subscriptions may issue a \texttt{resources/subscribe} request naming a specific URI; thereafter, whenever the resource's content changes, the server emits a \texttt{notifications/resources/updated} notification carrying that URI, and the client may re-issue \texttt{resources/read} to fetch the updated content \autocite{Sekar2026MCP}. This push-based model is particularly valuable for agentic workflows in which the model monitors a live data source—such as a CI pipeline output or a streaming log file—and must react to state changes without polling at a fixed interval.

For cases where the exact set of resources cannot be enumerated in advance—for instance, a server that provides access to an arbitrary filesystem or a database containing a dynamic number of tables—the specification defines \emph{resource templates} \autocite{mcpspec2025}. A resource template is a URI template conforming to RFC 6570 in which variable segments are delimited by curly braces; clients enumerate templates via \texttt{resources/templates/list} and instantiate them by substituting concrete values into the template variables to produce a fully resolved URI, which they then pass to \texttt{resources/read}. Template variables may be auto-completed through a complementary completion API, allowing IDE-style suggestion of valid parameter values when a user or the model is composing a resource request. The architectural distinction between resources and tools is therefore not merely semantic: resources are designed to be \emph{read} by the model as static or periodically refreshed context, whereas tools are designed to be \emph{invoked} to produce side effects or perform computations; conflating the two would undermine the host's ability to apply different access-control and caching policies to each category \autocite{Ray_2025}.

\subsection{Logging and Observability}
\label{subsec:mcp-logging}

The MCP specification defines a structured logging mechanism through which servers can emit diagnostic messages to clients throughout the lifetime of a session, enabling real-time observability of server-side behaviour without requiring out-of-band log aggregation infrastructure. A server that wishes to use this facility must declare the \texttt{logging} capability during initialisation; thereafter it may send \texttt{notifications/message} JSON-RPC notifications at any point during the operation phase \autocite{mcpspec2025}. Each notification carries three fields: \texttt{level}, a severity string drawn from the eight-level syslog vocabulary defined in RFC 5424 (\texttt{debug}, \texttt{info}, \texttt{notice}, \texttt{warning}, \texttt{error}, \texttt{critical}, \texttt{alert}, and \texttt{emergency}); \texttt{logger}, an optional string that identifies the subsystem or component emitting the message, such as \texttt{"database"} or \texttt{"http-client"}; and \texttt{data}, an arbitrary JSON-serialisable value that carries the structured payload of the message \autocite{Sekar2026MCP}. Because \texttt{data} is a free-form JSON field rather than a plain string, log messages can carry rich contextual objects—connection parameters, stack traces, latency measurements—that downstream log processing tools can parse and index without further string extraction. Clients may control the verbosity of the log stream by sending a \texttt{logging/setLevel} request specifying a minimum severity; the server SHOULD suppress all notifications below the requested threshold, allowing a developer to switch from \texttt{debug}-level tracing during initial development to \texttt{error}-only monitoring in production without restarting the server or modifying its configuration.

For long-running operations—such as indexing a large codebase, executing a multi-step batch query, or streaming the output of a slow external API—the protocol provides a complementary progress-notification mechanism \autocite{Ray_2025}. A client that wants to track the progress of a particular request includes a \texttt{progressToken} value (a unique string or integer) in the \texttt{\_meta} field of its request parameters. The server may then emit \texttt{notifications/progress} notifications referencing that token at whatever frequency it deems appropriate, each carrying a monotonically increasing \texttt{progress} value, an optional \texttt{total} against which progress can be normalised, and an optional human-readable \texttt{message} describing the current operation stage \autocite{mcpspec2025}. Together, structured logging and progress notifications give the host application the observability primitives it needs to build responsive user interfaces—displaying activity indicators, estimated completion times, and diagnostic panels—as well as the audit trails required for debugging, performance profiling, and security review of server-side behaviour \autocite{hou2025modelcontextprotocolmcp}. Implementations are advised to rate-limit both log messages and progress notifications to prevent a high-frequency server from overwhelming the client's message-processing capacity, and log content must be scrubbed of credentials, personally identifiable information, and internal system details that could assist an attacker if the log stream were intercepted.

\subsection{Execution and Validation Layer}
\label{subsec:mcp-execution}

Underlying all three server-side capability groups is a shared execution and validation layer whose responsibilities span from the moment a JSON-RPC message arrives at the server's transport interface to the moment a response or notification is dispatched. The outermost layer of validation is syntactic: the server must parse each incoming byte stream as valid JSON and then verify that the resulting value conforms to the JSON-RPC 2.0 envelope—a \texttt{jsonrpc} field set to the string \texttt{"2.0"}, a non-null \texttt{id} for requests, and a \texttt{method} string identifying the operation. Failures at this stage map to the standard JSON-RPC parse error code \texttt{-32700} (parse error) or \texttt{-32600} (invalid request), which are returned as JSON-RPC error responses and signal to the client that the message was malformed before any application logic was engaged \autocite{mcpspec2025}. If the method name is syntactically valid but does not correspond to any operation the server implements, the server returns error code \texttt{-32601} (method not found), preserving the clean separation between protocol-level failures and application-level failures.

For \texttt{tools/call} requests, semantic validation is performed against the tool's declared \texttt{inputSchema} before any execution takes place \autocite{Hasan2025MCPFirstGlance}. The server evaluates the \texttt{arguments} object in the incoming request against the JSON Schema stored in the tool definition, checking for the presence of all required fields, the correctness of all declared types, and compliance with any additional constraints such as \texttt{minimum}, \texttt{maximum}, \texttt{pattern}, or \texttt{enum} restrictions. A schema-validation failure surfaces as error code \texttt{-32602} (invalid params), providing the client—and through it the language model—with a structured signal that the invocation was rejected due to malformed arguments, not because of a server-side runtime fault. This early, schema-driven rejection serves two purposes: it protects the underlying tool implementation from receiving malformed input that could trigger undefined or security-sensitive behaviour, and it gives the model actionable feedback that enables it to self-correct its argument construction before retrying the call \autocite{Ray_2025}. Unexpected runtime failures that occur after successful validation are reported as error code \texttt{-32603} (internal error), completing the five-code error taxonomy that the JSON-RPC 2.0 specification reserves for standard protocol diagnostics.

The execution layer also enforces the capability-based access model established during initialisation. Because each server declares its supported primitives once, at session start, any client attempt to invoke a method outside the negotiated capability set can be rejected immediately—without consulting any tool registry or resource store—as a \texttt{-32601} method-not-found error \autocite{mcpspec2025architecture}. This design ensures that the server's security perimeter is defined by its capability declaration rather than by runtime filtering logic scattered across individual method handlers, making it straightforward to audit and reason about what a given server can and cannot do. Furthermore, the architecture's isolation principle—servers receive only the contextual information the host chooses to send them, and do not have visibility into the outputs of other connected servers—means that a compromised or malicious server cannot leverage its position in one tool invocation to gather information about other parts of the system \autocite{hou2025modelcontextprotocolmcp}. The combination of JSON Schema validation, standardised error codes, and capability-bounded method dispatch constitutes a coherent, layered defence against both inadvertent misuse and deliberate exploitation of the server interface.



\section{Limitations and Workarounds}
\label{sec:limitations}

Despite its architectural elegance and rapidly growing adoption, the Model Context Protocol is not without limitations. The original specification imposed transport constraints that complicated deployment in modern cloud environments, LLMs bring their own capability ceilings that no protocol design can fully overcome, and the agentic loops that MCP enables can amplify rather than contain the reliability weaknesses inherent in probabilistic language model inference. This section surveys the most significant of these limitations across three dimensions---transport layer design, task-level performance in software engineering settings, and systemic reliability in the face of hallucination---and describes the workarounds and mitigations that have been developed to address each.

\subsection{HTTP Limitations}
\label{subsec:http-limitations}

The original MCP specification (version 2024-11-05) defined two transport mechanisms: a \emph{stdio} transport for local deployments and an \emph{HTTP with Server-Sent Events} (HTTP+SSE) transport for network-accessible servers. While both transports were functional for their intended contexts, each carried architectural constraints that became problematic as MCP deployment scenarios diversified beyond the initial local-developer-tooling use case.

The \emph{stdio} transport is inherently local: the MCP client spawns the server as a child process and communicates exclusively through that process's standard input and output streams \autocite{mcpspec2025}. This design is simple, low-overhead, and free of network configuration concerns, but it fundamentally cannot support remote or multi-tenant deployments. A stdio-based server runs on the same machine as the client and is limited to serving a single client instance; empirical measurements have shown that concurrent access patterns collapse entirely under modest load, with the majority of requests failing under simultaneous connections \autocite{Ray_2025}. Process lifecycle management also introduces complexity: the server's lifespan is tied to the client process, so a client crash terminates the server abruptly, and any in-progress state is lost without a recovery mechanism. For organisations wishing to deploy MCP servers as shared, cloud-hosted services accessible to multiple users or AI agents simultaneously, stdio is architecturally unsuitable.

The HTTP+SSE transport was intended to close this gap by enabling network-accessible servers, but its design introduced a different class of problems rooted in the asymmetry of Server-Sent Events. SSE is a unidirectional HTTP mechanism: it provides a persistent, long-lived channel over which a server can push messages to a connected client, but it carries no provision for the client to send data through the same connection \autocite{mcpspec2025transports2024}. Consequently, the original specification required \emph{two} separate HTTP endpoints: a GET-accessible SSE endpoint that the client opened to receive server-to-client messages, and a distinct POST endpoint to which the client sent its own requests. This dual-endpoint architecture imposed a correlated connection-management burden on both parties, required explicit routing logic to associate POST requests with the correct SSE channel, and created a coupling between the two connections whose breakage---when either channel dropped---left the other in an indeterminate state. More critically, the requirement for persistent, long-lived SSE connections clashed directly with the assumptions of modern cloud infrastructure: load balancers, reverse proxies, serverless execution environments, and CDN edge nodes are all designed around short, stateless HTTP exchanges, and many either terminate idle persistent connections after a configurable timeout or route successive requests from the same logical session to different backend instances, destroying the association between the SSE and POST channels \autocite{Alla2025FastMCP}. The absence of any built-in resumability mechanism compounded this fragility: a network interruption during a long-running agentic task meant that the entire session had to be restarted from scratch, with no protocol-level provision for replaying missed messages.

\subsection{Streamable HTTP}
\label{subsec:streamable-http}

In response to these shortcomings, the MCP specification revision dated 2025-03-26 introduced a new transport mechanism called \emph{Streamable HTTP}, which replaces the old HTTP+SSE transport entirely \autocite{mcpspec2025transports}. The core architectural change is the consolidation of two separate endpoints into a single HTTP endpoint---typically served at a path such as \texttt{/mcp}---that accepts both POST and GET requests. All client-to-server messages are sent as HTTP POST requests to this endpoint; the server responds with either a \texttt{Content-Type: application/json} single response for simple synchronous interactions, or a \texttt{Content-Type: text/event-stream} SSE stream when the operation warrants incremental push notifications or server-to-client requests. The client may also issue a GET request to the same endpoint at any time to open a standing SSE channel for receiving unsolicited server notifications, without first needing to submit any POST request. This unified surface eliminates the correlation logic required by the old design and removes the architectural asymmetry that made the HTTP+SSE transport so difficult to deploy behind standard web infrastructure \autocite{mcpspec2025transports}.

A particularly significant property of Streamable HTTP is that it supports fully stateless server implementations. In the old transport, the persistent SSE channel was the carrier of server identity: a stateless server instance could not meaningfully participate because the SSE connection carried session state implicitly. Streamable HTTP externalises session identity to an explicit \texttt{Mcp-Session-Id} HTTP header: servers that wish to maintain session state issue this header in their initialisation response, and clients include it in all subsequent requests; servers that do not require session continuity may omit it entirely, enabling purely stateless, request-scoped implementations. A stateless MCP server can be deployed directly on serverless platforms such as AWS Lambda, Google Cloud Run, or Cloudflare Workers, where there is no persistent process to maintain a long-lived connection and each invocation is independent. This alignment with the serverless execution model opens MCP to a far broader deployment surface than was possible under the previous transport, and it means that standard load balancers, CDN edge nodes, and API gateways can be placed in front of MCP servers without any special configuration \autocite{mcpspec2025transports}.

Streamable HTTP also introduces optional resumability for SSE streams, addressing the connection-fragility problem that affected the earlier transport. Servers may attach a unique \texttt{id} field to each SSE event; if a client's connection drops, it can reconnect by issuing a new GET request with a \texttt{Last-Event-ID} header, and the server may replay any messages sent after that identifier, allowing the session to continue without loss \autocite{mcpspec2025transports}. A backwards-compatibility negotiation procedure is defined for clients that need to interoperate with servers still running the old protocol version: the client first attempts a POST \texttt{initialize} request; if the server returns an HTTP 4xx error, the client falls back to the legacy GET-then-POST SSE pattern. This negotiation ensures that the ecosystem-wide migration to Streamable HTTP can proceed incrementally without forcing simultaneous updates to all clients and servers \autocite{mcpspec2025transports}.

\subsection{Limitations in Coding Tasks}
\label{subsec:coding-limitations}

When MCP is deployed to support software engineering agents---the use case that drove much of the protocol's early adoption---the practical performance ceiling is set not by protocol design but by the capabilities of the underlying language models. Benchmarks on real-world coding tasks reveal that even state-of-the-art models, equipped with rich MCP tool suites, fall significantly short of human expert performance. The SWE-bench Pro leaderboard, which evaluates agents on enterprise-grade, multi-file issues drawn from real GitHub repositories, records a top score of approximately 59\% for the best-resourced configurations, with most evaluated systems falling in the 23--52\% range \autocite{scale_swebench_pro}. The gap between these figures and the higher scores reported on the earlier SWE-bench Verified benchmark is itself informative: \citeauthor{scale_swebench_pro} attribute a substantial portion of the inflation in Verified scores to benchmark contamination, where models have been exposed to the test problems during training, and recommend SWE-bench Pro as a more realistic measure of an agent's actual problem-solving capability on novel tasks.

A primary driver of failure in MCP-assisted coding agents is context window exhaustion. Every tool invocation injects additional tokens into the model's context: the tool schema occupies tokens before the call, the result occupies tokens after it, and intermediate reasoning traces further consume the available budget. In multi-step tasks---such as navigating a large codebase, reading multiple source files, running tests, and iteratively applying patches---the cumulative token cost can exhaust even large context windows before the task is complete, forcing premature truncation or requiring the agent to discard earlier observations \autocite{Fan2025MCPToolBenchPP}. The MCP-Universe benchmark quantifies the performance degradation that accompanies this phenomenon: token consumption escalates with each interaction step, and the benchmark explicitly identifies long-context degradation as one of three primary challenge categories, alongside unfamiliarity with novel tool APIs and cross-domain performance inconsistency \autocite{Luo2025MCPUniverse}. Even the best proprietary model evaluated on MCP-Universe---GPT-5---achieves an overall success rate of only 43.72\% in the multi-step ReAct track, underscoring that context exhaustion and multi-step compounding error are not marginal concerns but central failure modes.

Beyond context constraints, error propagation in agentic loops poses a structural reliability problem. In a multi-step coding task, each tool call produces an observation that is fed back into the model's context as the basis for the next decision. If a single tool call returns an erroneous result---due to a wrong file path, an incorrect patch, or a misunderstood API response---the model may incorporate that error into subsequent reasoning, compounding the mistake across later steps rather than recognising and correcting it. \textcite{Fan2025MCPToolBenchPP} document this pattern in MCPToolBench++: even when predictions are structurally correct at the schema level, actual execution is hampered by parameter mismatches and API idiosyncrasies that introduce errors early in a task sequence, and these errors propagate through the agentic loop in ways that simple schema validation cannot prevent. A further complication is cross-file dependency: resolving real software issues typically requires understanding the relationships between multiple source files, build configurations, and test suites. Without explicit context injection of all relevant files---which exacerbates the context window problem---models frequently make changes that are locally syntactically correct but semantically inconsistent with the broader codebase, a limitation that none of the currently evaluated systems have solved reliably \autocite{Luo2025MCPUniverse}.

\subsection{Reliability and Hallucination Mitigation}
\label{subsec:reliability}

Language models can hallucinate tool invocations---invoking tools that do not exist, supplying arguments whose names or types do not match the declared schema, or generating parameter values that are syntactically plausible but semantically incorrect. Production MCP deployments report hallucination rates for tool calls in the range of 2--8\%, and while individual hallucinations may appear infrequent, they occur at every step of a multi-step task; in a ten-step agentic loop, a 5\% per-step error rate means the probability of at least one error exceeds 40\% \autocite{Hasan2025MCPFirstGlance}. The MCP architecture's first line of defence against this class of failure is JSON Schema validation at the server boundary: because every MCP tool declares a precise \texttt{inputSchema}, the server can reject malformed invocations with a structured error code before any side effect occurs, and the error message is returned to the model's context so that it can attempt self-correction on the next generation step. \textcite{Hasan2025MCPFirstGlance} confirm that rigorous server-side schema enforcement---checking required fields, type constraints, and value ranges---substantially reduces the incidence of downstream execution failures caused by parameter errors, though it cannot address cases where the model selects the wrong tool entirely or supplies semantically incorrect but schema-valid arguments.

Structured output forcing, also known as constrained decoding, provides a complementary mitigation at the model inference layer. By constraining the model's token generation to produce only outputs that are parseable as valid JSON conforming to a target schema, hosts can guarantee that tool call requests are structurally well-formed before they are dispatched to the server, eliminating an entire class of parse-level failures. In practice, structured outputs are most effective for preventing argument-level hallucination---wrong field names, type mismatches, invalid enum values---while doing less to prevent higher-level semantic errors such as invoking the wrong tool or providing a plausible-looking but incorrect file path \autocite{Hasan2025MCPFirstGlance}. For the category of failures that structural validation cannot catch, the most widely adopted mitigation is the \emph{retry with reflection} pattern: when a tool call fails or produces an unexpected result, the agent is prompted to reason explicitly about the nature of the failure before retrying, a form of chain-of-thought error diagnosis that empirically achieves autonomous recovery rates of 70--80\% in controlled evaluations \autocite{Ray_2025}.

Human-in-the-loop checkpoints represent a higher-level reliability mechanism that the MCP specification actively endorses through its sampling and elicitation primitives. For operations carrying \texttt{destructiveHint: true}---such as deleting records, sending network requests, or committing code changes---hosts can pause agentic execution and require explicit user confirmation before proceeding, ensuring that catastrophic or irreversible actions are subject to human review. Complementing these protocol-native checkpoints, dedicated evaluation and observability platforms such as Langfuse provide session-level tracing of every tool call and its result, enabling post-hoc analysis of failure patterns, latency distributions, and hallucination rates across deployed systems \autocite{langfuse_evaluation}. Production systems also routinely implement timeout and circuit-breaker patterns at the client layer: each outgoing tool call is given a maximum execution time after which the client returns a synthetic error to the model, and a circuit breaker tracks the error rate of each individual server over a rolling window, temporarily suspending calls to servers that are returning errors at a rate above a configurable threshold. Together, schema validation, constrained decoding, reflective retry, human oversight, and infrastructure-level circuit breaking form a layered defence that substantially reduces---though cannot eliminate---the reliability gap introduced by the probabilistic nature of LLM inference in long-horizon agentic tasks \autocite{Hasan2025MCPFirstGlance}.



\section{Tool Usage and Orchestration}
\label{sec:tool-orchestration}

The preceding sections established how LLMs acquire tool-calling behaviour through training and structured output mechanisms, and how MCP concretises that behaviour into a standardised, protocol-level interface. What they left implicit is how these two layers combine at runtime to accomplish tasks that require more than a single inference step. \textbf{Tool orchestration} refers to the coordinated, multi-step use of external tools by an LLM agent, in which each tool call produces an observation that informs the next decision, and the process continues until the task is complete or a termination condition is reached \autocite{wang2023agents}. In an MCP-based system, the host application manages this orchestration loop: it routes the model's tool-call requests to the appropriate MCP servers, collects their results, injects those results back into the conversation context, and re-submits the updated context to the model for the next generation step. Understanding how this loop operates in practice—and how agents make decisions within it—is essential for appreciating both the power and the failure modes of MCP-based agentic systems.

\subsection{Tool Orchestration Loop}
\label{subsec:orchestration-loop}

The MCP-based tool orchestration loop begins before the model produces its first response. During context assembly, the host queries each connected server via \texttt{tools/list} and injects the resulting tool schemas—each containing a name, a natural language description, and a JSON Schema for the parameters—into the system prompt or a dedicated tools section of the context window \autocite{mcpspec2025tools}. The model thus perceives the available tools not through any special mechanism but through the same token stream it uses for all other information; the tool descriptions are, in effect, documentation that the model reads before deciding how to act. Empirical studies confirm that the quality and precision of these descriptions have a direct and substantial effect on the model's tool-selection accuracy: vague or ambiguous descriptions lead to incorrect tool choices and malformed argument construction, while well-specified descriptions with concrete examples of intended use significantly improve invocation correctness \autocite{Fan2025MCPToolBenchPP}. This observation—that tool schemas function as machine-readable documentation whose prose content directly shapes model behaviour—underscores a design principle that distinguishes MCP from lower-level function-calling APIs: the protocol treats the description field as a first-class artefact, not a cosmetic annotation.

Once the model determines that a tool call is warranted, it emits a structured \texttt{tool\_use} content block containing the tool name and a JSON-serialised arguments object. The host inspects the stop reason of the model's response: a stop reason of \texttt{tool\_use} indicates that the model expects execution to continue after the tool result is returned, whereas a stop reason of \texttt{end\_turn} signals that the model considers its task complete and is not requesting any further tool invocation \autocite{mcpspec2025architecture}. When the stop reason is \texttt{tool\_use}, the host routes the request to the MCP client managing the relevant server, which issues a \texttt{tools/call} JSON-RPC request; the server executes the underlying operation and returns a typed result content array, which the host appends to the conversation as a \texttt{tool} role turn. The updated conversation—now containing the original task, any intermediate reasoning, the tool call, and the tool result—is re-submitted to the model, which either produces another tool call, reasons over the accumulated evidence, or generates a final response for the user. Modern LLM providers also support \textbf{parallel tool calls}, in which the model emits multiple \texttt{tool\_use} blocks in a single response; the host dispatches all of them concurrently to their respective MCP servers, collects the results, and returns them together in a single context update, substantially reducing wall-clock latency for tasks whose sub-steps are independent \autocite{mcpspec2025tools}.

A particularly important property of the loop is \textbf{tool call chaining}: the output of one tool call can serve directly as an argument to a subsequent call, enabling multi-step pipelines in which the model first retrieves information and then acts on it. For example, an agent resolving a software issue might call a \texttt{search\_codebase} tool to identify the relevant file, pass the returned file path to a \texttt{read\_file} tool to retrieve the source text, and then pass the source text to a \texttt{apply\_patch} tool to implement the fix—each step conditioning on the result of the previous one. The host's role in this chain is purely mechanical: it appends each result to the context and resubmits, without imposing any task-specific control flow. This design places the full burden of sequencing, dependency management, and termination detection on the model itself, which means that the quality of the system prompt—particularly its instructions about when to stop, how to handle partial results, and what constitutes task completion—is a primary determinant of orchestration reliability \autocite{Luo2025MCPUniverse}. Practitioners therefore invest significant effort in crafting system prompts that constrain the tool selection scope, establish clear stopping criteria, and provide examples of correct multi-step invocation patterns, treating the system prompt as the orchestration policy rather than a simple role description.

\subsection{Decision-Making and Iterative Execution}
\label{subsec:decision-making}

The dominant framework for reasoning about how an LLM agent makes decisions within an orchestration loop is the \textbf{ReAct} pattern, introduced by \textcite{yao2022react}. In ReAct, the model interleaves explicit reasoning traces (\emph{Thought}) with concrete tool invocations (\emph{Action}) and incorporates the returned observations (\emph{Observe}) before producing the next thought. This Thought--Action--Observe cycle maps directly onto the MCP orchestration loop: the model's reasoning trace corresponds to the chain-of-thought text that precedes a \texttt{tool\_use} block, the tool invocation is the \texttt{tools/call} request dispatched by the host, and the observation is the tool result appended to the context. \textcite{yao2022react} demonstrated empirically that this interleaved approach substantially outperforms both pure chain-of-thought reasoning and pure action-based execution, because the explicit reasoning steps allow the model to detect errors early and revise its plan in response to unexpected observations before those errors compound across subsequent steps. In MCP-based deployments, the ReAct pattern is typically instantiated through the system prompt, which instructs the model to reason before each tool call and to evaluate the result before deciding on the next action. An alternative planning paradigm, \textbf{Plan-and-Execute}, separates the task into an upfront planning phase—in which the model produces a complete, ordered list of sub-tasks—and a sequential execution phase, in which each sub-task is carried out by invoking the appropriate tools \autocite{wang2023agents}. Plan-and-Execute is advantageous when the task structure is predictable and when the cost of replanning mid-task is high, but it is less adaptive than ReAct to tasks whose scope evolves as new information is uncovered during execution.

The choice between sequential and parallel tool execution is itself a decision that well-designed agents must make dynamically. Sequential execution is necessary when the output of one tool is the input to the next, forming a dependency chain that cannot be resolved out of order. Parallel execution is preferable when multiple tools can be invoked simultaneously without dependency, as it reduces total latency and avoids unnecessary context growth from intermediate reasoning between independent calls \autocite{mcpspec2025tools}. In practice, most agentic tasks involve a mixture of both patterns: an initial parallel burst of information-gathering tool calls is followed by sequential, dependency-ordered tool calls that act on the retrieved information. Error recovery is a further dimension of the decision-making process. When a \texttt{tools/call} response carries \texttt{isError: true}, the model receives a structured signal that execution failed, along with a human-readable error description in the content array \autocite{mcpspec2025}. The model can then reason about the failure—inspecting the error message, identifying the likely cause, and deciding whether to retry with corrected arguments, invoke an alternative tool that achieves the same goal through a different mechanism, or escalate to the user via the elicitation primitive. \textcite{Fan2025MCPToolBenchPP} report that models equipped with explicit retry-and-reflection instructions in their system prompts recover autonomously from tool call failures at substantially higher rates than models that receive only a generic error message, confirming that the error recovery strategy is largely a function of prompt design rather than model capability alone.

Termination is the final and often most overlooked component of the decision-making process. An agent that does not know when to stop will continue invoking tools until its context window is exhausted, its iteration budget is exceeded, or a human intervenes. The MCP specification does not prescribe termination logic; it is the responsibility of the host application and the system prompt to define termination conditions explicitly. In production deployments, three complementary mechanisms are typically combined: a \emph{task completion signal}, in which the model produces an \texttt{end\_turn} response without any \texttt{tool\_use} blocks, indicating that it has satisfied the user's request; a \emph{maximum iteration budget}, enforced by the host as a hard cap on the number of \texttt{tools/call} round trips within a single session; and \emph{human interruption}, enabled by the MCP elicitation primitive, which allows the host to pause the agentic loop and solicit user guidance at any point \autocite{wang2023agents}. The role of the system prompt in governing termination is particularly consequential: a system prompt that defines the task goal precisely and provides examples of what a complete response looks like enables the model to produce reliable \texttt{end\_turn} signals, whereas an underspecified prompt leads to agents that either terminate prematurely, before all necessary steps have been completed, or continue indefinitely, applying redundant tool calls to a task that is already resolved \autocite{Luo2025MCPUniverse}. Together, the ReAct reasoning pattern, dynamic parallelism decisions, structured error recovery, and explicit termination policies constitute the decision-making layer that transforms the mechanical orchestration loop into a capable, robust agentic system.
